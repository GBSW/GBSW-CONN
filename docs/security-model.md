# 보안 위협 모델

## Overview

이 저장소는 약 200~220명의 학교 공동체가 사용하는 개인정보·익명성 민감 웹 애플리케이션을 제공한다. 주요 런타임 표면은 Next.js 브라우저 UI, Spring Boot REST API, MySQL 데이터베이스, 향후 공식 공시 API 어댑터다. 가장 중요한 자산은 익명 작성자의 실제 신원, 계정과 세션, 비공개 동의 관계, 고충 내용, 심의와 신원 열람 기록, 공식 답변과 재정 공개 데이터의 무결성, 비밀 키와 백업이다.

공격자는 인터넷의 비인증 사용자뿐 아니라 정상 학생 계정을 가진 숙련된 보안 학생, 탈취된 교사 계정 사용자, 권한을 오용하려는 내부 운영자를 포함한다. 슈퍼 어드민도 익명 신원을 단독으로 열람할 수 없는 것이 제품 불변조건이다.

## Threat Model, Trust Boundaries, and Assumptions

### 신뢰 경계

1. 브라우저와 동일 출처 웹 계층 사이: 모든 입력, 쿠키, 공개 ID, 헤더는 공격자 통제 가능하다.
2. Next.js와 Spring Boot 사이: 프록시는 편의 경계일 뿐 신뢰 경계가 아니다. 백엔드는 모든 인증·권한을 재검증한다.
3. Spring Boot와 MySQL 사이: 애플리케이션 DB 계정 권한을 최소화하고 Flyway 운영 권한과 런타임 권한의 분리를 목표로 한다.
4. 일반 업무 데이터와 Identity Vault 사이: 일반 제안 조회 코드가 평문 신원이나 복호화 기능에 접근하지 못한다.
5. 애플리케이션/DB와 비밀 저장소 사이: 암호화 키, DB 비밀번호, 외부 API 키는 Git과 DB 밖에 둔다.
6. 공개 저장소와 비공개 운영 영역 사이: 실제 계정, 로그, 백업, 연결정보, 인프라 세부사항을 공개 저장소에 반입하지 않는다.
7. 공식 외부 API와 내부 공개 데이터 사이: 응답을 신뢰하지 않고 출처, 스키마, URL 허용목록과 검증 상태를 확인한다.

### 입력 소유권

- 공격자 통제: 로그인 ID/비밀번호, 제안·신고·고충 본문, 공개 ID, 페이지·정렬 값, CSRF 시도, 요청 순서와 동시성, 외부 출처 URL 후보.
- 운영자 통제: 계정/보직 임명, 재정 공개 자료, 운영 설정, 사건 생성 사유. 운영자 입력도 권한과 검증을 거친다.
- 개발자 통제: Flyway, 의존성, CI, 예제 설정. 실제 비밀과 개인정보를 포함하지 않는다.

### 보안 불변조건과 가정

- 권한은 기본 거부하며 UI 가시성은 권한 증명이 아니다.
- 50명 미만 제안은 학생과 배정된 심의 관계자 외 교사에게 노출되지 않는다.
- 제안 일반 모델·응답·로그·검색·분석에는 익명 작성자 내부 ID가 없다.
- 신원 열람은 독립 사건의 3인 전원 승인, 배정된 학생부장, 최근 재인증이 모두 필요하다.
- 동의는 활성 학생 1인 1표이고 DB 고유 제약이 최종 통제다.
- 공개 제한은 물리 삭제가 아니며 신원 확인과 독립적이다.
- 운영은 HTTPS와 신뢰 가능한 비밀 저장소를 제공한다고 가정한다. 그렇지 않으면 프로덕션 배포 조건을 충족하지 않는다.
- 운영 서버에 대한 무단 보안 시험과 사회공학은 허용 범위 밖이다. 제공된 시험 환경에서만 검증한다.

## Attack Surface, Mitigations, and Attacker Stories

| 표면 | 현실적인 공격 이야기 | 계획된 통제 |
| --- | --- | --- |
| 로그인·활성화·재설정 | 계정 열거, 무차별 대입, 코드 탈취, 세션 고정 | 일반화 오류, Argon2id, 해시된 일회 코드, 계정+IP 영속 제한, 세션 회전 |
| 객체 API | 공개 UUID를 바꿔 타인의 고충/제안/심의 접근 | 서비스 수준 객체 권한, 최소 404/403 노출, BOLA 통합 테스트 |
| 제안·동의 | 병렬 중복 동의, 투표 수 조작, 50명 승격 중복 | DB 고유 제약, DB 카운트, 잠금/조건부 갱신, 단일 트랜잭션 |
| 콘텐츠 출력 | 저장형 XSS로 세션 또는 교사 작업 탈취 | HTML 실행 금지, React 기본 이스케이프, 요청별 nonce CSP, 위험 렌더링 API 금지 |
| 심의 | 보직 변경, 표 위조, 사건 유형 혼합으로 신원 우회 | 심의자 스냅샷, 사건별 1표, 타입 분리, 전원 승인 서버 검증 |
| Identity Vault | 일반 조회·예외·로그·백업에서 신원 유출 | 별도 테이블/서비스, AEAD와 키 버전, DTO allowlist, 로그 마스킹 |
| 재정·외부 URL | 허위 자료, SSRF, 비공개 대상 공개 | 공식 출처 어댑터, HTTPS 호스트 허용목록, 검증자, 외부 연동 기본 비활성 |
| 운영·공급망 | 비밀 커밋, 취약 의존성, 악성 마이그레이션 | `.env.example`, 잠금 파일, 의존성 검사, CODEOWNERS/PR 검토, 최소 DB 권한 |

특히 중요한 실패 유형은 기능/객체 권한 우회, 세션 탈취, CSRF, 저장형 XSS, 익명 신원 측면 채널, SQL/JPQL 주입, SSRF, 과도한 요청 크기, 민감 로그, 백업/키 관리 실패다. 첨부파일은 MVP에서 없어 파일 업로드 취약점은 현재 공격 표면 밖이다. 다중 서버 분산 속도 제한도 단일 서버 전제에서는 낮은 우선순위지만, 확장 시 설계를 재검토한다.

## Severity Calibration (Critical, High, Medium, Low)

- **Critical**: 인증 없이 또는 일반 학생이 익명 신원 대량 복호화, 임의 코드 실행, 전체 계정 자격 증명/키/운영 DB를 획득하는 경우. 3인 심의와 학생부장 재인증을 모두 우회해 신원을 대량 열람하는 경로도 여기에 해당할 수 있다.
- **High**: 일반 학생이 타인의 비공개 고충을 읽거나, 교사/운영자 권한을 얻거나, 다수의 동의를 위조해 안건을 승격하거나, 저장형 XSS로 고권한 사용자의 세션/행동을 탈취하는 경우.
- **Medium**: 계정 존재를 신뢰성 있게 열거하거나, 제한된 범위의 비민감 데이터 무결성을 깨거나, 한 사용자/사건에 지속적인 서비스 거부를 일으키거나, 민감 메타데이터를 제한적으로 노출하는 경우.
- **Low**: 보안 경계를 넘지 않는 경미한 정보 노출, 제한이 쉬운 저영향 과도 요청, 개인정보가 없는 개발 환경의 진단 정보처럼 현실적 영향이 작은 경우. 단, 같은 원인이 운영 비밀·신원에 닿으면 상향한다.

위협 모델은 구현과 함께 갱신한다. 실제 운영 환경의 TLS, 백업, 키 관리, 로그 접근 통제가 정해지면 현재 가정을 운영 통제로 교체해야 한다.
