# 핵심 정보 구조와 저해상도 흐름

이 문서는 대규모 UI 구현 전에 검토할 제품 흐름이다. 색상·로고·학교 공식 자산은 확정하지 않고, 설명형 이름인 “학교 소통 제안 시스템”만 사용한다.

## 학생 첫 화면

```text
[학교 소통 제안 시스템]                     [내 활동] [로그아웃]

새로운 제안을 살펴보고, 공감하는 제안에 동의해 주세요.
[제안 작성]  [정식 안건 보기]

제안 탐색
[전체 제안 ▾] [최신순 ▾] [검색________________]

  범위: 전체 제안 · 정식 안건 · 채택 안 됨
  정렬: 최신순 · 날짜순 · 동의 많은 순 · 동의 적은 순
  검색: 제목과 본문에서 부분 일치로 찾는다

제목                         상태             동의
기숙사 ○○ 개선 제안          동의 모집 중      32 / 50
수업 ○○ 운영 제안            정식 안건          67
```

첫 화면의 주 행동은 탐색, 동의, 작성, 학교 답변 확인이다. 통계 카드와 관리자형 대시보드는 두지 않는다.

## 작성 경로 선택

```text
어떤 내용을 전하고 싶나요?

공개 학교 개선 제안
학생들에게 공개되며, 50명 이상의 동의를 받으면 학교가 검토하는 정식 안건이 됩니다.
[공개 제안 작성]

비공개 개인 고충·안전 제보
학교폭력, 자해 위험, 개인정보, 성희롱, 차별처럼 공개 투표로 다루면 안 되는 내용입니다.
[비공개로 도움 요청]
```

두 경로를 하나의 폼이나 공개 여부 토글로 합치지 않는다.

## 공개 제안 작성

```text
제목 [________________________________]
내용 [________________________________]
     [________________________________]

작성자 표시
(●) 익명으로 공개  ( ) 이름 공개
익명을 선택해도 남용 대응을 위한 연결정보는 보호된 영역에 보관됩니다.

[취소] [제안 등록]
```

욕설이나 비판 표현을 사전 차단하지 않는다. HTML/스크립트 실행은 허용하지 않는다.

구현된 화면은 `/proposals`, `/proposals/new`, `/proposals/{publicId}`로 분리한다. 피드는 최신순을 기본으로 하고 동의 모집 중에는 `현재 / 50`을 항상 표시한다. 정식 안건에서는 승격 당시 동의 수와 현재 유효 동의 수를 구분해 표시하며, 정식 안건 이후에는 동의 철회 동작을 제공하지 않는다.

## 교사 진입

```text
검토할 정식 안건

제목                    승격 시각       상태
수업 ○○ 운영 제안       8월 2일         검토 전
```

교사 대시보드는 정식 안건과 검토 대기 제안을 별도 목록으로 나누어 보여주며, 검토 대기 목록은 동의수 내림차순이다. 익명 작성자는 어느 목록에서도 `익명`으로만 표시한다.

정식 안건 상세에서 내부 지정된 현재 담당 교사에게만 상태에 맞는 단일 명령 폼을 표시한다. `검토 시작 → 채택/보류/반려 → 실행 시작 → 완료`의 허용 경로만 제공하고, 보류 상태에는 검토 재개만 제공한다. 담당자가 아닌 교사에게는 조회만 허용한다.

학생 상세에는 학교 공식 답변, 결정 사유, 후속 계획, 답변 시각과 진행 이력을 표시한다. 담당·응답 교사의 이름이나 계정 식별자는 표시하지 않는다.

## 신원 확인 흐름

```text
사건 생성 → 사건 시점 3인 배정 → 각자 승인/거부 → 전원 승인
→ 학생부장교사 최근 재인증 → 사유 확인 → 1회 신원 열람 + 감사 기록
```

학생회장과 부회장 화면에는 승인 판단에 필요한 콘텐츠와 사유만 표시하며 이름·학번·복호화 결과를 포함하지 않는다.

구현 화면은 제안 상세의 신고 폼, `/moderation`의 학생부장교사 신고함과 고정 심의자 사건함, `/moderation/{publicId}`의 사건 자료·의결·학생부장교사 일회 열람 영역으로 나뉜다. 공개 제한과 신원 확인은 각각 사건 생성 사유와 의결을 받는다. 신원 열람은 학생부장교사가 화면에서 비밀번호 재인증과 열람 사유를 함께 입력하며, 결과는 현재 컴포넌트 메모리에만 두고 닫은 뒤 재조회하지 않는다.

## 슈퍼 어드민 계정 관리

```text
세션·최근 본인 확인 상태
→ 새 계정 생성 또는 계정 검색·선택
→ 계정 상태와 전체 역할·보직 이력 확인
→ 가입/재설정 코드 발급, 정지·재활성화, 임기 추가·종료
→ 민감 작업 시 비밀번호 재확인 후 작업 재시도
```

가입 코드와 비밀번호 재설정 코드는 응답 직후 화면 메모리에만 표시한다. 운영자가 안전한 경로로 전달한 뒤 직접 지울 수 있으며 브라우저 저장소에는 보관하지 않는다. 목록은 현재 유효한 역할·보직만 빠르게 보여주고, 선택 계정의 상세 영역에서 종료 이력을 함께 확인한다.

`/admin/proposals`는 제안 본문 없이 정식 안건 제목·상태와 내부 담당 정보만 표시한다. 슈퍼 어드민은 최근 재인증 후 활성 교사를 지정하거나 변경한다. 변경 전 담당 이력은 보존되고 학생 화면에는 공개되지 않는다.

## 검토가 필요한 지점

2026-08-02 사용자 검토 결과:

1. 학생 제안 목록의 기본 정렬은 최신순으로 한다.
2. 동의 모집 중에는 동의 수를 `32 / 50`처럼 임계값과 함께 항상 표시한다. 정식 안건은 승격 당시 동의 수와 현재 표시 정책을 구현 단계에서 구분한다.
3. 작성 경로 선택 화면에는 실제 담당 부서명이나 별도 긴급 상황 안내 문구를 추가하지 않는다. 단, 비공개 고충의 서버 열람 권한은 보안 정책이므로 담당자 확정 전까지 기능을 활성화하지 않는다.
4. 정식 안건 담당 교사는 학생 화면과 일반 학생용 API에 표시하지 않는다. 교사 업무 부담을 늘릴 수 있는 개인 담당자 공개 기능을 만들지 않는다.
5. 학교 공식 로고·교표·색상은 사용하지 않는다. 정식 서비스명과 함께 자체 로고와 브랜드 컬러를 추후 설계한다.

2026-08-05 제안 목록 결정:

1. 정렬은 `최신순`(등록일 내림차순), `날짜순`(등록일 오름차순), `동의 많은 순`, `동의 적은 순` 네 가지를 제공한다. 기능구현 명세서의 `최신순`과 `날짜순`을 서로 다른 기준으로 확정해 두 선택지가 실제로 다른 결과를 낸다.
2. 동의 수가 같은 항목은 등록일, 그다음 내부 식별자 순으로 정렬한다. 이 고정 기준이 없으면 같은 조건으로 다시 조회했을 때 순서가 달라져 페이지를 넘길 때 항목이 중복되거나 빠질 수 있다.
3. 범위 필터는 `전체 제안`, `정식 안건`, `채택 안 됨` 세 가지다. `채택 안 됨`은 담당 교사가 반려한 제안을 가리킨다.
4. 검색은 제목과 본문을 함께 찾는다. 기능구현 명세서는 `안건명으로 검색`이라고 적었으나, 본문까지 찾는 편이 실제로 더 유용하고 이미 그렇게 동작하고 있어 현재 동작을 정본으로 삼는다.
5. 공식 용어는 `정식 안건`으로 통일한다. `공식 안건`은 쓰지 않는다.
