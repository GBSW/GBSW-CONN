# 운영 준비 체크리스트

현재 저장소는 로컬 개발만 지원하며 배포 승인을 받지 않았다. 다음 항목이 확정·검증되기 전에는 운영에 사용하지 않는다.

## 배포 전

- TLS 종료와 HTTP→HTTPS 강제
- `prod` 프로필, Secure 쿠키, Swagger 비활성 확인
- 애플리케이션과 Flyway DB 권한 분리
- DB 비밀번호, 익명 신원 암호화 키, HMAC 키, 외부 API 키의 비밀 저장소 등록
- 키 버전과 회전·폐기 절차
- 암호화 백업, 별도 접근 권한, 복원 시험, RPO/RTO 승인
- 실제 개인정보와 익명 연결정보의 보존/파기 기간 승인
- 운영 로그 접근 권한, 보존 기간, 민감정보 마스킹 검증
- 2명 이상의 Organization Owner와 비공개 보안 신고 채널
- main 보호, 필수 CI, CODEOWNERS 승인, secret scanning과 push protection

## 마이그레이션

1. 운영 백업과 복원 가능성을 확인한다.
2. 릴리스 노트의 스키마 변경과 호환성을 검토한다.
3. 실제 운영과 같은 MySQL 버전의 복제 환경에서 Flyway를 처음부터 적용하고 업그레이드 경로를 시험한다.
4. 적용 중 실패 시 서비스 중단, 롤포워드, 백업 복원 중 어떤 절차를 사용할지 승인한다.
5. 이미 적용된 Flyway 파일을 수정하지 않는다.

## 최초 슈퍼 어드민

1. DB, `THROTTLE_FINGERPRINT_SECRET`, `PROPOSAL_IDENTITY_KEY_BASE64`를 비밀 저장소에서 공급한다.
2. 저장소 밖 또는 Git에서 제외된 디렉터리를 만들고 `BOOTSTRAP_OUTPUT_FILE`로 지정한다.
3. `BOOTSTRAP_LOGIN_ID`, `BOOTSTRAP_DISPLAY_NAME`과 출력 경로만 환경변수로 전달해 `backend/gradlew bootstrapSuperAdmin`을 실행한다.
4. 소유자 전용 `0600` 파일의 개인 가입 코드를 본인에게만 전달하고 `/activate`에서 즉시 소비한다.
5. 활성화와 로그인 성공을 확인한 뒤 코드 파일을 안전하게 폐기한다.

명령은 DB 마커로 한 번만 성공한다. 실패했다고 수동 SQL로 마커나 관리자를 추가하지 말고 감사 로그와 Flyway 상태를 확인한다. 가입 코드 원문을 티켓, 메신저 단체방, 셸 기록이나 운영 로그에 복사하지 않는다.

## 익명 제안 Identity Vault 키

- `PROPOSAL_IDENTITY_KEY_BASE64`는 정확히 32바이트의 무작위 키를 Base64로 인코딩한 값이어야 하며 소스, Git, DB에 저장하지 않는다.
- `PROPOSAL_IDENTITY_KEY_VERSION`은 새 암호문에 기록되는 양의 버전이다. 기존 행을 재암호화하고 복구 시험을 마치기 전에는 버전이나 키를 교체하지 않는다.
- 키가 없거나 형식이 잘못되면 애플리케이션이 시작되지 않는 것이 정상이다. 임시 기본 키로 우회하지 않는다.
- 키 노출 시 제안 생성과 신원 관련 기능을 먼저 차단하고, 승인된 오프라인 재암호화·감사 절차와 백업 복원 가능성을 확인한 뒤 회전한다.

## 정식 안건 담당과 공식 답변

- 담당 지정·변경은 슈퍼 어드민 최근 재인증 후 `/admin/proposals`에서 수행한다.
- 대상 교사의 계정이 활성 상태이고 현재 `TEACHER` 역할 임기인지 확인한다. 역할 종료나 계정 정지 뒤에는 기존 지정이 남아 있어도 상태 명령이 거부된다.
- 담당 변경 이력, 업무 상태 이력, 공식 답변, 감사 로그를 직접 수정하거나 삭제하지 않는다.
- 학생에게 전달되는 응답과 로그에 담당·응답 교사 식별 정보가 포함되지 않는지 릴리스 전 계약 테스트를 확인한다.
- 공식 답변 기한은 아직 확정되지 않았으므로 알림 기한이나 자동 상태 변경 숫자를 추가하지 않는다.

## 신고 심의와 신원 열람

- 새 사건을 만들기 전에 학생부장교사·학생회장·학생부회장 현임자가 정확히 한 명씩이고 각 역할이 유효한지 확인한다. 공석 또는 역할 불일치 상태에서는 사건 생성이 거부되는 것이 정상이다.
- 기존 사건의 심의자는 보직 변경으로 교체하지 않는다. 사건 당시 스냅샷, 의결, 공개 상태 이력과 신원 열람 기록을 직접 수정하거나 삭제하지 않는다.
- 신원 확인 승인과 실제 열람을 구분한다. 승인 후에도 고정 배정된 학생부장교사만 최근 재인증과 사유 입력을 거쳐 한 번 열람할 수 있다.
- 열람 응답을 화면 캡처, 티켓, 브라우저 저장소나 일반 로그에 복사하지 않는다. 감사 로그에는 열람 사건과 행위자만 남고 평문 로그인 ID·이름이 포함되지 않는지 릴리스 전 통합 테스트를 확인한다.
- 공개 제한은 물리 삭제가 아니다. 재심·복구 정책이 승인되기 전에는 DB 행이나 공개 상태 이력을 수동 변경하지 않는다.

## 사고 대응

- 세션/계정 침해: 계정 정지, 모든 세션 폐기, 자격 증명 재설정, 감사 로그 보존
- 비밀 노출: 즉시 폐기·회전하고 Git 기록과 로그/빌드 산출물까지 영향 범위를 확인
- 익명 신원 노출: 추가 열람 차단, 최소 증거 보존, 비공개 조사, 영향 사용자 보호 절차 우선
- 데이터 무결성 사고: 쓰기 경로 격리, 감사/DB 로그 보존, 검증된 백업 또는 롤포워드 계획 실행

구체적인 운영 사업자, 서버, 도메인, 연락처와 법정 보존 기간은 미정이다.
